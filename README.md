# Accessibility RAG Fixer

This tool scans React and React Native JSX/TSX source files for missing
accessibility props, asks a local Ollama model to propose fixes, and checks
the proposed changes before keeping them.

## How the pipeline works

1. **Load accessibility rules.** The scanner reads
   `accessibility-component-rules.json`, which maps component names to
   required accessibility props.
2. **Scan source code.** `scanner.py` finds JSX component tags and reports
   props that are missing according to the rules and a few fallback
   heuristics.
3. **Retrieve rule context.** `run_fixer.py` embeds the affected component
   names with `all-minilm`, compares them to the rule embeddings in
   `vector_store.json`, and selects the closest rule descriptions.
4. **Generate a candidate fix.** The retrieved rules, scan findings, and
   complete source file are sent to the configured Ollama chat model.
5. **Validate the candidate.** The fixer rejects output that appears
   truncated, writes the candidate temporarily, and scans it again. It keeps
   the change only if the scanner finds no remaining issues in that file;
   otherwise, it restores the original file.

The scanner and validation are deterministic Python code. The AI model only
proposes the updated source code; it does not decide which components the
scanner recognizes.

## Files

### `accessibility-component-rules.json`

The human-maintained source of truth for scanner requirements. Each category
lists component names and the props expected on those components. For
example, button components are configured to require an accessibility label,
role, and hint.

The scanner reads this file whenever the fixer runs. Edit it to change which
components or props are checked.

### `scanner.py`

Implements the rule-based scan:

- `load_rules()` turns the category-based JSON into a component-to-props map.
- `find_jsx_elements()` searches source text for capitalized JSX component
  tags and extracts their attributes and line numbers.
- `scan_file()` finds missing props and returns issue records.
- `generate_project_report()` scans source files under a project and writes
  `reports/accessibility-report.json`.

The scanner also uses simple heuristics for some components not in the rules,
such as elements with `onPress` or IDs with recognized prefixes.

### `index_rules.py`

Builds the semantic index used during retrieval. It converts each rule into a
short text description, creates an embedding for that text with Ollama's
`all-minilm` model, and writes the descriptions and vectors to
`vector_store.json`.

Run this again after changing the rules so the retrieval index stays in sync.

### `vector_store.json`

Generated data, not the source of truth. It stores rule descriptions and
their numeric embeddings. `run_fixer.py` uses it to find rule descriptions
that are semantically similar to the affected component names. The scanner
does not use this file to decide which props are missing.

Do not edit this file by hand; regenerate it with `index_rules.py`.

### `setup_model.py`

Creates the custom Ollama model `ally-fixer`, based on
`qwen2.5-coder:3b`, and assigns it a system prompt describing how to make
accessibility fixes. This configures a model from an existing base model; it
does not fine-tune or train the base model.

The model name can be changed with the `A11Y_FIXER_MODEL` environment
variable. `run_fixer.py` uses the same variable to select the model for
generation.

### `run_fixer.py`

The command-line entry point and pipeline coordinator. It handles single
files and project folders, groups findings by file, retrieves relevant
rules, asks Ollama to generate updated code, then validates and saves or
reverts each candidate.

For a single file, it writes a scan report to the project's `reports`
directory before attempting fixes. The default generation model is
`ally-fixer`; the default embedding model is `all-minilm`.

## Setup

### Prerequisites

- Python 3.10 or later.
- Ollama installed and running on the same machine (or reachable at the
  configured Ollama server address).
- The `qwen2.5-coder:3b` generation model and `all-minilm` embedding model.
- A terminal opened in the `a11y-rag-fixer` directory for the commands below.

Install Ollama from [ollama.com/download](https://ollama.com/download) and
start the Ollama application before running the fixer. The `ollama` command
should be available in a new terminal.

### Windows (PowerShell)

Open PowerShell in the `a11y-rag-fixer` directory. Create and activate a
virtual environment, then install the Python Ollama client:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install ollama
```

If PowerShell blocks activation of the virtual environment, either allow
scripts for the current user according to your organization's policy, or
invoke the environment's Python directly as
`.venv\Scripts\python.exe` instead of activating it.

Pull the required models, generate the vector store, and register the custom
fixer model:

```powershell
ollama pull qwen2.5-coder:3b
ollama pull all-minilm
python index_rules.py
python setup_model.py
```

### macOS (Terminal)

Install Python 3.10 or later if it is not already available, then install
Ollama from [ollama.com/download](https://ollama.com/download). Open the
Ollama app and leave it running. In Terminal, change to the `a11y-rag-fixer`
directory and create a virtual environment:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install ollama
```

Pull the required models, generate the vector store, and register the custom
fixer model:

```bash
ollama pull qwen2.5-coder:3b
ollama pull all-minilm
python index_rules.py
python setup_model.py
```

The virtual environment only needs to be created once. In later terminal
sessions, go to the `a11y-rag-fixer` directory and activate it again before
running Python commands:

```powershell
# Windows PowerShell
.\.venv\Scripts\Activate.ps1
```

```bash
# macOS
source .venv/bin/activate
```

If the rules change, rerun `python index_rules.py` to rebuild
`vector_store.json`. If the custom Ollama model needs to be created again,
rerun `python setup_model.py`. The commands require Ollama to be running and
the required base models to be available.

## Running

From the `a11y-rag-fixer` directory, pass a source file or project folder:

```powershell
python run_fixer.py ..\react-a11y-demo\src\screens\LoginScreens.tsx
```

To select another Ollama generation model, set the environment variable
before running the script:

```powershell
$env:A11Y_FIXER_MODEL = "ally-fixer"
python run_fixer.py ..\react-a11y-demo\src\screens\LoginScreens.tsx
```

## Rules versus vector store

These files have different jobs:

- **Rules JSON:** tells the scanner exactly which props to check. Changes
  take effect on the next scan.
- **Vector store:** helps retrieve relevant rule text for the AI prompt.
  Regenerate it with `python index_rules.py` after rule changes.

The scanner checks the rules directly; the vector store does not replace
that check.

## Limitations

- JSX parsing is implemented with regular expressions and a small custom
  parser, not a complete TypeScript/JSX parser. Unusual or complex syntax can
  be missed or parsed incorrectly.
- Only components covered by the rules or fallback heuristics are checked.
- Retrieval ranks rule descriptions by cosine similarity of embeddings; it
  is not a full understanding of the component's implementation.
- The validation pass only checks whether this scanner still reports
  missing props. It does not prove that the generated code compiles or that
  the UI is accessible to users. Review changes and run the project's
  formatter, type checker, tests, and accessibility checks as appropriate.
